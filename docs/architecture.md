# Boşa Gezme! backend architecture

## Product boundary and decisions

Boşa Gezme! is a modular Go monolith for discovering and reviewing real home/living store locations. Its canonical product domain is `bosagezme.com`. PostgreSQL is the system of record; PostGIS provides indexed geographic filtering and distance checks. External systems sit behind narrow interfaces. Stores exist independently of users, so a later claim/merchant model can reference `stores` without changing store identity.

The feed is keyset-paginated: reverse chronology without location, and stable viewer-to-store distance followed by reverse chronology when a coordinate pair is supplied. Manual discovery location text is resolved server-side through Google Places, filtered to geographic place types, and never treated as visit evidence. Search intent is parsed deterministically first and optionally enriched by AI; only validated domain fields reach SQL. Aggregates are transactionally updated in `store_stats`, while normalized social tables remain authoritative and a recalculation command repairs drift.

Domain packages own explicit SQL. Interfaces are limited to OpenAI, Places, email, object storage, push, and Google-token verification boundaries.

## B. PostgreSQL schema

All public IDs are UUIDs generated by PostgreSQL. Soft-deletable entities have `deleted_at`; normal queries explicitly exclude them.

| Area | Tables and important constraints/indexes |
|---|---|
| Identity | `users(primary_email citext unique where active)`, `auth_identities(provider,provider_subject unique; provider,normalized_email unique where verified)`, `auth_sessions(refresh_token_hash unique, family_id, replaced_by, revoked_at)`, hashed single-use `email_verification_codes` |
| Profiles | one-to-one `user_profiles` (public) with optional bio language; `user_private_profiles` holds optional demographics and the private current/manual discovery location as PostGIS geography; private `users.preferred_locale` |
| Anonymous | `visitor_sessions(id, linked_user_id, locale, expires_at)`; its ID is analytics correlation, never authentication |
| Stores | language-independent `stores` with `geography(Point,4326)` and GiST index; canonical category keys plus `store_category_translations`; optional descriptive `store_translations`; `store_external_sources(provider,external_id unique)`; one-to-one `store_stats` |
| Social | `posts` and `comments` preserve original UGC plus optional `content_language`; rating and derived visit distance/time; single-use expiring `store_visit_verifications`; `media`, ordered `post_media`; unique favorites/likes/follows; self-follow check |
| Search | `searches` with Unicode raw text, canonical validated intent, `query_language` and privacy-rounded coordinates; `search_results(search_id,rank unique)`; idempotent `search_interactions` |
| Delivery | locale-persisted OTP/email jobs; locale/template-key/parameters on push devices and notification jobs; delivery records and preferences |

Important indexes cover provider identity, active sessions, feed `(created_at,id)`, user/store posts, available visit proofs, all social uniqueness keys, search owner/history, result rank, outbox availability, and geographic GiST lookup. Exact submitted review/visit coordinates are not retained; only distance, reported accuracy, and server verification time are stored. Search coordinates are rounded according to configuration and can be deleted/anonymized by retention jobs.

## C. Authentication design

Email request creates a six-digit code with `crypto/rand`, stores only an HMAC-SHA256 digest keyed by `OTP_HASH_SECRET`, and atomically enqueues an email. Codes expire, have an attempt cap, are single-use, and request/verify paths are limited by client, IP, email and visitor ID. The API does not wait for email delivery.

Verification locks the code row. Identity creation runs in one serializable transaction:

1. Look up the trusted identity by `(provider, subject)`.
2. If absent, lock/find an active user by normalized *verified* email.
3. Create the user only if none exists, then insert the identity.
4. Unique constraints are the final concurrency guard; a unique race retries the transaction and resolves the winning user.

Google ID tokens are verified server-side for signature, issuer, audience, expiry and verified email. Unverified Google emails are never used for linking. Provider subject remains the durable identity key.

Access JWTs are short-lived and include user/session IDs, issuer `https://bosagezme.com`, audience `bosagezme-clients`, and token type. Opaque random refresh tokens are stored only as keyed hashes. Rotation locks the current session, revokes it, and creates a replacement in the same family. Reuse of a revoked/replaced token revokes the whole family. Logout revokes one family/session; logout-all revokes all active sessions for the user. The brand migration changes the issuer/audience, so access tokens minted before deployment are rejected; their normal lifetime is 15 minutes by default and valid refresh sessions mint the new token identity.

## D. Security design

`/health` and `/ready` disclose only status. Every `/v1/*` route first passes constant-time `X-BFF-Secret` validation against all configured `BFF_SECRETS`; values and sensitive headers are never logged. This client credential is independent from user auth.

Optional auth accepts no token or a valid access token; an invalid supplied token is rejected. Required auth additionally demands an authenticated principal. Owner checks are performed in transactional mutations. Rate-limit classes use bounded in-process token buckets now and can later be backed by Redis without changing handlers. JSON bodies are bounded, unknown fields rejected, server timeouts enforced, panics recovered, and request IDs propagated.

A mobile-embedded BFF secret can be extracted and is only a coarse client gate. The middleware is deliberately replaceable by a client-verifier interface so App Attest, Play Integrity, or short-lived gateway credentials can replace it.

Current-location reviews are checked with PostGIS against the configured store radius; when supplied, horizontal accuracy is added conservatively to the measured distance. A mobile client can verify while on site and receive a server-timestamped proof bound to that user and store. Proofs expire, are consumed atomically by one review, never accept client-supplied historical time as evidence, and are removed by privacy maintenance after their operational retention window. This limits replay and fabricated-history attacks, while device-level location spoofing remains a platform-attestation concern rather than something coordinates alone can eliminate.

The API emits no permissive CORS headers, so browsers deny cross-origin calls by
default; a deployment gateway may add an explicit origin allowlist when the web
BFF origin is known. Client identity and rate limiting deliberately use the
socket peer address and do not trust `X-Forwarded-For` from arbitrary callers.
When deployed behind a trusted proxy, normalize the peer address at that edge or
add a narrowly configured trusted-proxy layer rather than accepting forwarded
headers globally.

## E. Search architecture

```text
raw query -> deterministic parser -> optional OpenAI scope/intent enrichment
                                      |
                    +-----------------+-------------------+
                    |                                     |
          out_of_scope / unclear                    home_living
          localized guidance only                         |
                                          +---------------+---------------+
                                          |                               |
                             internal Postgres search             Google Places
                                          |                               |
                                          +---------------+---------------+
                                                          |
                               provider-ID match, conservative dedupe, ranking
                                                          |
                                      persist search + impressions -> response
```

The two home/living providers run concurrently. Results with at least one proximity-verified Boşa Gezme! review receive a ranking tier above Google-only results; community and Google rating snapshots remain separate. Out-of-scope and unclear requests do not invoke either store provider. A Google-only result is materialized only after the backend refetches provider details; `(provider,external_id)` uniqueness makes this concurrency-safe. Provider retention is configuration-driven and raw Places payloads are not stored.

Search accepts Turkish, English, German and Russian through one pipeline.
Unicode-aware normalization preserves Cyrillic and performs only targeted accent
folding for useful equivalents such as `Kadıköy`/`kadikoy`. The deterministic and
OpenAI parsers emit the same canonical store-name/category/product/style/price identifiers. Bare recognized home/living store names are valid discovery intent.
PostgreSQL uses the language-neutral `simple` configuration together with
canonical taxonomy, PostGIS and provider search; it does not pretend that one
language dictionary covers all four languages. Google receives a locale hint,
while its stable Place ID—not localized name/address—is the identity key.

## F. OpenAI integration

Only the raw query plus coarse locale/location context is sent. The official OpenAI Go SDK calls the Responses API with a strict JSON schema for store name, scope, categories, products, styles, price intent, attributes, location and sort preference. The response is size-bounded, decoded with unknown-field rejection, enumerations/lengths/radius/coordinates are validated, and it is merged only into fields allowed by the deterministic parser.

The call has a strict configurable timeout. Empty keys, timeout, provider error, refusal, malformed JSON or invalid domain values produce a logged metric/status and deterministic fallback—not a failed search. AI never produces SQL, authorization, visit verification, or final ranking.

## G. Internationalization architecture

Supported locales are centrally registered as `tr`, `en`, `de`, and `ru`; the
configurable default is `tr`. Request locale precedence is: valid explicit
`X-Locale`, authenticated user's private `preferred_locale`, valid
`Accept-Language`, then default. Regional variants are normalized and unsupported
or malformed hints fall back rather than rejecting an otherwise valid request.
Locale is immutable request context, so concurrent requests cannot leak language.

Translatable data is deliberately classified:

1. Application copy (API errors, OTP email and notification templates) uses
   version-controlled resources whose locale key sets are completeness-tested.
2. Domain taxonomy uses stable machine keys and row-based localized translations.
   A fifth language adds rows/resources rather than schema columns.
3. User-generated and external content remains original; optional language
   metadata is stored without automatic translation. Official store identity and
   Google Place ID remain language-independent.

Machine-readable API error codes are stable across locales. Only presentation
messages change. Asynchronous OTP/email and notification records persist locale,
so workers never depend on a later request context. Locale/search-language
analytics use dimensional rows rather than one column per language, and private
locale/search information follows existing deletion and retention boundaries.

## I. Threat model

| Threat | Primary controls / residual risk |
|---|---|
| BFF leakage | rotation list, constant-time compare, no logging, per-client limits; mobile extraction remains possible |
| Token theft | short access TTL, hashed rotating refresh tokens, family reuse detection, logout-all, TLS required |
| OTP brute force | keyed hash, short TTL, attempt cap, single use, layered limits, generic responses |
| Google token abuse | official signature/audience/issuer/expiry verification; only verified email links |
| Fake GPS | server distance calculation and radius; GPS can be spoofed, so future attestation/receipt signals fit a visit-verifier boundary |
| Duplicate accounts/stores | transactions, row locks, verified-email policy, unique provider IDs, retry on unique races |
| Spam/social abuse | auth, body limits, write limits, ownership checks, soft deletion; moderation is a later layer |
| Search/OpenAI abuse | BFF gate, IP/user/session quotas, timeout, bounded inputs/outputs, deterministic fallback and cost metrics |
| Sensitive data exposure | public/private profile split, derived visit data, rounded search locations, deletion and retention hooks, redacted logs |
